# Архитектура

Описывает целевую архитектуру. Разделы с пометкой **(план)** ещё не реализованы.

## Расположение в проекте и в DataModel

| Папка | В Roblox | Что внутри |
|---|---|---|
| `src/shared` | `ReplicatedStorage.Shared` | Config, Domain, общие типы. Видно клиенту: ничего секретного |
| `src/server` | `ServerScriptService.Server` | Сервисы, точка входа сервера, серверная часть Zap |
| `src/client` | `StarterPlayer.StarterPlayerScripts.Client` | Контроллеры, UI (Vide), точка входа клиента, клиентская часть Zap |
| `Packages` | `ReplicatedStorage.Packages` | Общие пакеты Wally (Vide) |
| `ServerPackages` | `ServerStorage.ServerPackages` | Серверные пакеты Wally (ProfileStore) |
| `net/remotes.zap` | — | Контракт сети; генерирует `src/*/Net/Remotes.luau` |
| `assets` **(план)** | `ReplicatedStorage.Assets` | Модели `.rbxm` |
| `lune` | — | Скрипты задач: install, check, test, format, net |
| `tests` | — | Тесты доменной логики для Lune |

Настройки Workspace задаются в `default.project.json`: `StreamingEnabled = true` (выключить нельзя: Server Authority держит его включённым), `StreamingMinRadius = 1024`, `StreamingTargetRadius = 2048` (радиус больше карты, чтобы мир из тысячи частей приходил целиком, а не кусками; решение 032), `SignalBehavior = Deferred`, `AuthorityMode = Server`, `FallenPartsDestroyHeight = -5000`. Свойства Workspace плагин Rojo в открытый плейс не записывает — в новом плейсе их один раз выставляют вручную (Workspace → Properties): `AuthorityMode = Server` (связанные свойства, в том числе `StreamingEnabled`, включаются сами и больше не выключаются), `StreamingMinRadius = 1024`, `StreamingTargetRadius = 2048`.

## Слои

```
Config       данные: зоны, стражи, существа, редкости, цены, тайминги.
             Числа — чистый Luau (читаются в Lune: тесты, калькулятор);
             внешний вид с Color3/Vector3/Enum — отдельно, в *Looks
   ↓
Domain       чистая логика без Roblox API: BigNum, вес яйца, мозг стража, вылупление,
             скрещивание, отсек, офлайн-прогресс, миграции профиля
   ↓
Services     сервер: связывает Domain с Roblox (данные, физика, мир, сеть)
Controllers  клиент: ввод (Input Action System), камера, UI, эффекты
   ↓
Net          сгенерированный Zap + наш слой команд и репликации
```

Зависимости идут только вниз по схеме. `Domain` не импортирует ничего из Roblox, поэтому тестируется в Lune.

## Запуск

Один `Script` на сервере (`src/server/Main.server.luau`) и один `LocalScript` на клиенте (`src/client/Main.client.luau`). Фреймворков вроде Knit нет: точка входа создаёт сервисы, явно передаёт им зависимости и отдаёт список в `Lifecycle.run` (`src/shared/Runtime/Lifecycle.luau`).

Сервис — таблица `{ name, init?, start?, ...API }`, создаётся функцией `new(...)`. Две фазы:
1. **`init`** — у всех сервисов по порядку. Связать зависимости, создать объекты. Синхронно: `Lifecycle` падает с ошибкой, если `init` ждёт.
2. **`start`** — у всех сервисов, каждый в своём потоке. Подключить события и начать работу.

Игроки обрабатываются через `PlayerEvents.observe` (`src/server/Runtime`): обработчик одинаково вызывается для уже подключённых и для новых игроков.

## Данные игрока

```
DataService (связь с Roblox: игроки, сообщения при ошибке)
  └─ SessionManager (чистый Luau: жизненный цикл сессии, тестируется в Lune)
       ├─ ProfilePort ── ProfileStoreAdapter ── ProfileStore
       └─ loadData ───── PlayerData.load (миграции, дополнение полей, проверка — на копии)
```

- **Жизненный цикл:** `Loading → Active → Closing → Closed`, а также `Failed` (не загрузилось, данные новее сервера, данные повреждены) `Closed (SessionLost)` (профиль открыли на другом сервере) и `Closed (ServerShutdown)` (сервер выключается, ProfileStore сам сохраняет и закрывает сессии; игрока никуда не отправляем — сообщение покажет Roblox).
- **Только `Active` принимает изменения:** `DataService.update(player, mutator)`. Мутатор не должен ждать — `SessionManager` падает с ошибкой, если он уступит поток. Сначала все проверки, потом запись.
- **Загрузка на копии.** `PlayerData.load` мигрирует, дополняет и проверяет копию. Оригинал в `Profile.Data` не трогается, пока всё не прошло; при неудаче профиль закрывается с исходными данными.
- **Не загрузилось — не играем.** Игрок получает сообщение на своём языке (`data.*.message`) и выходит.
- **Схема:** `src/shared/Domain/PlayerData.luau` — `SCHEMA_VERSION`, `MIGRATIONS`, `template(defaults)`. Деньги и ⚡ хранятся как `BigNum` — его форма совпадает с форматом сохранения. Стартовые значения из конфигов (`Defaults`: ⚡ новичка, число капсул) передаёт `DataService`: домен конфигов не читает.
- **Прокачка в профиле** (v3): `trained` (очки с тренажёра), `trainerLevel`, `jetpackLevel`. Показываемая ⚡ = `Upgrades.speed(trained, jetpackLevel)`; её публикует `SpeedService`. Миграция v2 → v3 переносит старое `speed` в `trained`.
- **Монеты за всё время** (v6): `coinsEarned` растёт вместе с балансом при каждом заработке и не падает от покупок; по нему ранжирует доска монет. Монеты в профиль приходят только через `Domain/Wallet.earn` — так новый источник не пройдёт мимо доски. Миграция v5 → v6 начинает счёт с текущего баланса; при загрузке `coinsEarned` не бывает меньше баланса.
- **Покупки за робуксы** (v14, решение 061): `purchaseIds` — последние 100 выданных чеков (`PurchaseId`), чтобы ни один не выдать дважды; `passes` — купленные пропуски (`Purchases.PassId`: копия на случай, если проверка Roblox не ответит); `pendingDouble` — монеты и ⚡ последнего возвращения для «Забрать ×2» (нули — забирать нечего). Что делает каждая покупка — чистый `Domain/Purchases`; какие ID у какой игры и числа — `MonetizationConfig` (в игре не из списка покупки выключены).
- **Туториал** (v15, решение 065): `tutorialStep` — сколько вех туториала пройдено (`Domain/Tutorial`: 0 — не начат, 4 — пройден). Миграция v14 → v15 считает пройденным игрока, уже доставлявшего от стража 2 и дальше (`bestPost`).
- **Игровое время** (v4): `playSeconds` копит `OfflineService` раз в секунду вместе с меткой `lastSeenAt`; по нему работает защита новичков (`Domain/Pvp`).
- **Отсек в профиле** (v2): `pods` (капсулы, в каждой пришелец или пусто), `inventory`, `floor` (вылупившиеся без места), `incubator` (яйца с unix-временем вылупления), `nextUid` (счётчик адресов пришельцев и яиц), `lastSeenAt` (метка для офлайн-дохода и офлайн-тренировки). Операции над отсеком — чистые функции `Domain/Bay`, вызываются внутри `DataService.update`.
- В Studio каждое изменение состояния сессии печатается в Output (`[DataService] User …: Active`).
- Чистые серверные модули (например, `SessionManager`) не делают `require` модулей из `ReplicatedStorage`: строковый `require` между `ServerScriptService` и `ReplicatedStorage` в Roblox не работает. Всё нужное им передаётся параметрами — заодно это делает их тестируемыми.

## Сеть

- `net/remotes.zap` — единственный контракт. После правки: `lune run net`. Строки — `string.utf8`; `BigNum` на проводе — та же пара мантисса/порядок, что в сохранении.
- **Данные игрока на клиент** (`NetService` → `ProfileState` на клиенте): `ProfileSnapshot` при активации профиля и по запросу `RequestSnapshot` (клиент просит, когда его контроллеры готовы), затем дельты по разделам: `CoinsChanged` (раз в секунду, когда доход не нулевой), `BayChanged` (отсек целиком после перестройки — он маленький, а разделение на «добавлен X» не стоило бы своей сложности), `OfflineReward`, `Hatched`, `Crossbred`, `UpgradesChanged`, `Trained`, `NoticeSent`; вместе с отсеком всегда уходят и монеты (почти каждое изменение отсека их меняет, а тик дохода шлёт их только пока что-то зарабатывает). Клиент держит копию в источниках Vide и не пишет в неё.
- **Команды** (`AutoPlace`, `MoveToPod`, `MoveToInventory`, `Crossbreed`, `Sell`, `BuyPod`, `UpgradeJetpack`): `NetService.guarded` — лимит частоты на игрока (`Domain/RateLimit`, `NetConfig`) → активный профиль → `EconomyService`, который проверяет смысл запроса на живом профиле, применяет одно изменение через `DataService.update` и перестраивает отсек. Отказ уходит клиенту как `NoticeSent` с причиной.
- Ввод, влияющий на симуляцию (полёт, захват), идёт через Input Action System, а не через remotes. Захват — одним нажатием (решение 070, бриф `docs/design/screens/grab-button.md`): симуляция ловит момент нажатия `Grab` (атрибут `GrabPressed`) и держит «зацепился» в атрибуте `GrabEngaged` (`Grab.nextEngaged`); пока зацеплен — магнит и прогресс. Клиент повторяет это для кнопки, подсказки на яйце и туториала в `State/GrabState`.

## Движение и Server Authority

Включено: `Workspace.AuthorityMode = Server` (решение 019). Сервер считает движение, клиент его предсказывает и откатывается при расхождении. Подделка позиции или скорости на клиенте откатывается движком.

```
Клиент                                   Сервер
AimController ─ направление камеры ─┐
стандартное управление (MoveDirection)├─> InputActions под Player ─> SpaceSimulation
Space/Ctrl, кнопки ▲▼ на телефоне ───┘                              (тот же модуль)
SpaceSimulation (предсказание) ─> атрибуты персонажа ─> HUD (Vide)
```

- **`SpaceSimulation`** (`src/shared/Simulation`) привязан через `RunService:BindToSimulation` на сервере и на клиенте. Над платформой (в пределах её радиуса, под куполом) — обычная ходьба; в остальном пространстве — полёт. Так при подлёте джетпак работает, пока игрок не окажется над полом, а при сходе с края включается сразу за ободом на `LinearVelocity` + `AlignOrientation` туда, куда смотрит камера; кислород убывает в космосе и восстанавливается под куполом.
- **Математика** — в `Domain/Flight`, `Domain/Oxygen`, `Domain/Zones`, покрыта тестами.
- **Ввод** (`src/shared/Input/FlightInputs`): контекст `FlightContext` под каждым `Player` (создаёт сервер). `Ascend`/`Descend` — клавиши и кнопки на телефоне (`UIButton`-привязки создаёт клиент локально), `Aim` — `Scriptable`-привязка, её каждый кадр заполняет `AimController`. Сервер не доверяет `Aim`: `Flight.sanitizeAim`.
- **Объекты создаются вне симуляции:** `SpaceService` выдаёт контекст ввода игроку и ограничители персонажу, убивает при пустом баллоне (в `PostSimulation`).
- **Состояние симуляции — в атрибутах персонажа:** `InSpace`, `Oxygen`. HUD читает их на клиенте — значения предсказанные, поэтому без задержки.

Правила кода в симуляции — в [CONVENTIONS.md](CONVENTIONS.md), раздел 5.

## Мир

`WorldService` строит мир при старте сервера, всё из кода: платформа станции со светящимся ободом, купол-пузырь на платформе и ступенчатый корпус под ней, точка появления, поле астероидов по зерну (`WorldConfig.SEED`, одинаковое на всех серверах), освещение космоса. Позже детали заменятся моделями из `assets/`.

**Отсеки.** `BayService` даёт каждому игроку отсек на его острове (`BayLooks`, `BayModel`; решение 068, бриф `docs/design/screens/island.md`), когда его профиль активен, и освобождает при выходе. Содержимое — места с пришельцами (раскладка по их размеру, `Domain/PlaceLayout`), капсулы инкубатора с яйцами, пришельцы на полу — строится из профиля и **перестраивается целиком** после каждого изменения (`refresh`): данных мало, зато мир не может разойтись с профилем. Клиент (`BayViewController`) рисует по тегам `Bay`, `Alien`, `IncubatorEgg` экраны терминалов, имя хозяина на доске, фишки и таймеры яиц; таймер яйца считает по `workspace:GetServerTimeNow()` против атрибута `HatchAt`.

Раз в секунду (общий планировщик) отсек делает один `DataService.update`: двигает яйца в бурю, считает готовые (`Bay.readyCount`; стало больше — отсек перестраивается, над готовым яйцом свет и подсказка «Вылупить») и начисляет доход капсул за прошедшее время. Вылупляет игрок (решение 059): подсказка у готового яйца — `ProximityPrompt` только для хозяина (атрибут `OwnerId`, чужие клиенты его не рисуют); сервер проверяет хозяина и дистанцию, `Bay.hatch` убирает яйцо и ставит на место первое ждущее с отсчётом от этой минуты, дальше `Hatch.pick` по удаче яйца → `Bay.addHatched` и сигнал `hatched`. Метку `lastSeenAt` раз в секунду двигает `OfflineService`; он же при активации профиля одним обновлением платит за время отсутствия: доход капсул (потолок 4 ч, с «Ночной сменой» 8 ч) и тренировку (50 %, потолок 8 ч, с «Ночной сменой» 16 ч; прибавка — `Purchases.trainerRate` с пропусками), запоминает выплату для «Забрать ×2» (`pendingDouble`), затем шлёт `OfflineReward` для экрана «С возвращением!» (и сколько яиц готово). Какие пропуски у игрока, видят все клиенты: атрибуты игрока `Passes` и `TrainerMultiplier` (их пишет `PurchaseService`). Доставка: `CarryService` на платформе отдаёт яйцо в `BayService.addEgg` с грейдом гнезда (`Bay.addEgg`: в свободное место инкубатора или в очередь `waiting`, решение 058; вне игры очередь стоит — готовые яйца держат места до возвращения; покупка места — `EconomyService.buyIncubatorSlot`; над каждым яйцом на месте — свой таймер, ждущие лежат на платформе вокруг инкубатора; грейд — `NestService.getGrade`: пост гнезда задаёт раскладка мира — у каждого поста зоны своё узкое кольцо внутри кольца зоны, первый пост ближе всех к станции, `Domain/NestLayout`, решение 057); стражи берут пост оттуда же. Подбор пришельца с пола — `ProximityPrompt` только для хозяина; сервер проверяет владельца, дистанцию и место в инвентаре.

**Тренажёр — стенд джетпака** (бриф `docs/design/screens/jetpack-stand.md`). Стоит у входа на остров (`BayConfig.TRAINER_PAD` в координатах острова, модель `Stand` в модели отсека, её главная часть — площадка `Trainer`; туториал подсвечивает всю модель). Пристёгивает симуляция (`SpaceSimulation.stand`, логика — `Domain/Stand`): хозяин в зоне своего стенда (остров — атрибут `Island` на `Player` от `BayService`) — его тянут на площадку и держат теми же `LinearVelocity`/`AlignOrientation`, что и в полёте, лицом к центру острова, с загруженной анимацией `StandConfig.ANIMATION_ID` (поза — `Character/StandPose`); прыжок или шаг — сходит, повторно — только после выхода из зоны. Состояние — атрибут `Stand` на персонаже. `TrainingService` раз в секунду платит тем, кого держит стенд, и одним `update` прибавляет `trained` на `Upgrades.trainerRate(level) × dt`; затем `SpeedService.publish` обновляет атрибуты ⚡, а событие `Trained` даёт клиенту всплывающую цифру (`TrainingViewController`). Пламя джетпака на стенде растёт с уровнем тренажёра (атрибут `TrainerLevel` на `Player`, `Stand.flameScale`), решётка за стендом светится, дежурные огоньки гаснут (`JetpackEffectsController`). Улучшение тренажёра — кнопка на экране его **терминала** (бриф `docs/design/screens/terminals.md`; кнопка только у хозяина) → команда `UpgradeTrainer` через калитку → `EconomyService.upgradeTrainer`. Места и капсулы инкубатора покупаются так же, на своих терминалах (`BuyPod`, `BuyIncubatorSlot`). Терминал — модель в отсеке (`BayModel`), экран — `SurfaceGui` на его части `Screen` (`UI/TerminalScreen`, в `PlayerGui`, чтобы кнопка нажималась). Уровень тренажёра и число мест лежат в атрибутах модели отсека (`TrainerLevel`, `PodCount`), яйца и места инкубатора — в атрибутах его части; по ним `BayViewController` рисует экраны; цену считает сам из конфигов. Подсказки «E» (подобрать пришельца, открыть магазин) — `ProximityPrompt` со `Style = Custom`, которые `PromptViewController` рисует тем же `GrabPrompt`, что и захват яйца.

**Джетпаки.** Один магазин на станции (`ShopModel`, `ShopLooks`, тег `Shop`): подсказка на прилавке открывает окно на клиенте (`ShopController` слушает `ProximityPromptService.PromptTriggered`), тексты подсказки и вывески клиент ставит сам на своём языке. Окно (`ShopWindow`) строится из копии профиля: уровни 0…n со статусами пройден / твой / купить / позже; покупка — команда `UpgradeJetpack` через калитку → `EconomyService.upgradeJetpack`. `JetpackService` держит уровень в атрибуте игрока `JetpackLevel` (по нему `JetpackEffectsController` у всех клиентов масштабирует огонь) и перекрашивает модель джетпака (`JetpackModel.applyLooks`, цвета по уровням в `JetpackLooks`); новый персонаж получает джетпак сразу своего уровня (`SpaceService` ← `getJetpackLooks`). Имена уровней — `Names.jetpack` по `UpgradeConfig.JETPACK_NAME_KEYS`.

**PvP.** Все способности — действия в `InputContext` полёта (удар ЛКМ/R2, гарпун F/Y, бомба G/B, кнопки на телефоне; щита нет — решение 060): под Server Authority сервер видит нажатие и прицел сам. `PvpService` раз в 1/15 с ловит нажатия, проверяет перезарядку и купол, а для атак — цель и `Domain/Pvp.refusal` (купол, новички по игровому времени `playSeconds`, 10 с после респауна, правило 10× по ⚡). Удар живёт в симуляции, а не в `PvpService`: `SpaceSimulation` по нажатию запускает выпад (`Abilities.stepStrike`, атрибуты персонажа `StrikeLunge`, `StrikeCooldown`, `StrikeAim` — предсказываются, так что у атакующего выпад без задержки) и проигрывает анимацию удара. `PvpService` каждый кадр после симуляции (`PostSimulation`) смотрит на идущие выпады: первая цель в радиусе касания перед атакующим (`Domain/Abilities.nearestInCone`) получает `Character/Knockback.apply` — те же атрибуты, что удар стража (`HitVelocity`, `HitAxis`, плюс `HitBy` — кто ударил) — и `CarryService.dropEgg`, в точке касания вспышка (`PvpEffects.strikeImpact`); выпад кончился без касания — промах. С яйцом в руках симуляция выпад не запускает. Перезарядку удара клиент читает прямо с персонажа. Анимация удара — данные `Character/StrikePose`, собираются `Character/PoseAnimation` (как полёт), загружаются вручную, ID — `PvpConfig.STRIKE_ANIMATION_ID`. Гарпун: ближайший носитель в узком конусе, яйцо летит к стрелку. Бомба: летит по прицелу, взрывается у цели или через секунду, бьёт всех в радиусе. Эффекты в грейбоксе делает сервер (`World/PvpEffects`). Отказ — тост через `NetService.notify`, результат — событие `AbilityResult` (с него клиент считает перезарядку в `AbilityState` для чипов HUD, а `PvpViewController` показывает тост попадания или выбитого яйца — промах без тоста); `PvpService.getUsage` считает использования для решения о магазине способностей. Защита новичка видна всем: атрибут игрока `NewbieSecondsLeft`. Для одиночных проверок — бот `SpawnDummyThief`, зарегистрированный через `PvpService.addCreature` (существо PvP, как Звёздный змей).

## Стражи (план)

- Без `Humanoid` и скелетных анимаций. **Сервер** держит стража серым телом с двигателями (`World/GuardianModel`: `LinearVelocity`, `AlignOrientation`, предсказание выключено): по нему ловит и гонится. **Вид — только клиент** (решение 090): `GuardianViewController` при появлении тела (стриминг) надевает на него модель поста (`World/GuardianVisual`: модель из `ReplicatedStorage.Guardians`, вставленная в плейс вручную, `lune run guardians`; краска — `AlienDress.paintModel`; размер — `Domain/GuardianPose.fitScale`), прячет серое тело и каждый кадр несёт модель на нём одним `BulkMoveTo`. Ближе `GuardianLooks.MODELS.MOTION_DISTANCE` части двигаются (`World/RigMotion`, общий с питомцами: роли деталей и шарниры), темп, челюсть и глотка — по состоянию (`GuardianLooks.STATE_MOTION`), глаза — в цвет состояния, при поимке — рывок (`GuardianPose.strike`); дальше модель неподвижна и переставляется, только когда тело сдвинулось. Поста без модели в плейсе — серый страж; `GuardianModel.checkPlace` в Studio предупреждает о недостающих и устаревших моделях.
- У гнезда одно яйцо в мире: `NestService` ведёт его цикл по `Domain/NestCycle` (в гнезде → унесено → растёт новое). Новое растёт только после `CarryService` → `NestService.eggDelivered`; невостребованное или брошенное яйцо возвращается через `returnEgg`.
- Конечный автомат на сервере (`GuardianBrain`): `Sleep → Chase → Return`; просыпается, когда яйцо гнезда унесли, с задержкой; с пути домой разворачивается, если яйцо взяли снова. «Дом» стража — над его яйцом: в гнезде или там, где оно выпало (`CarryService.findLooseEggs`; яйцо внутри границы станции не считается — туда стражу нельзя). Поводка и лимита времени нет: погоня кончается, только когда вор пропал или оказался внутри границы станции (сфера `StationConfig.BORDER_RADIUS` вокруг центра купола) либо в зоне станции. Сами стражи держатся за границей с запасом `GuardianConfig.BORDER_MARGIN` (`Bounds.keepOutside`). Границу в мире рисует `WorldService`: бледная сфера и кольцо из неоновых сегментов. Поведение у всех одинаковое, стражи отличаются видом и скоростью (`GuardianConfig`).
- Скорость полёта стража в погоне — по отношению ⚡ стража и вора (см. GAME_DESIGN, «Погоня»).
- Активны только рядом с игроками; тикают с пониженной частотой.

## Аналитика

`MetricsService` — единственное место, которое знает `AnalyticsService` Roblox. Остальные службы только сообщают факты своими сигналами (`CarryService.grabbed/reachedStation/delivered/lost`, `BayService.incomePaid`, `EconomyService.coinsTraded/crossbred`, `TrainingService.trained`, `OfflineService.settled`, `SpaceService.suffocated`, `PvpService.abilityUsed`), а `Main` передаёт их в `MetricsService`.

- **Воронка новичка** — `LogOnboardingFunnelStepEvent`, шаги из `Domain/Onboarding`; каждый шаг один раз на аккаунт, пройденные — битовой маской в профиле (`onboardingSteps`, схема v5).
- **Прогресс** — `LogProgressionCompleteEvent` по пути `Guardians` при первой доставке от поста дальше прежнего (`bestPost` в профиле).
- **Экономика** — `LogEconomyEvent`, валюты `Coins` и `Speed`; источники: доход пришельцев, продажа, офлайн, тренажёр (дальше — задания и подарки через `MetricsService.earned`); траты: капсула, тренажёр, джетпак.
- **Кража** — `LogFunnelStepEvent` воронки `Theft`, сессия на каждое взятое яйцо: взял → долетел до границы станции → доставил.
- **Свои события** — `LogCustomEvent`: `EggLost` (причина, зона), `GuardianCatch` (пост), `OxygenDeath` (зона), `Ability` (способность, итог), `Crossbreed` (ступень, зона).

Частые факты (доход каждую секунду, выплаты тренажёра, способности) суммируются по игроку и уходят раз в 5 минут и при выходе — так запросов меньше лимита Roblox (120 + 20 × онлайн в минуту). В полях нет имён игроков: число сочетаний значений ограничено. В Studio события не отправляются (Roblox их не принимает) — печатаются в Output с префиксом `[Metrics]`, сумма копится 30 секунд.

## Активность игроков (АФК)

`ActivityService` знает, кто реально играет, а кто отошёл от клавиатуры (`Domain/Activity`, `ActivityConfig`). Раз в секунду смотрит, где персонаж: сдвиг больше чем на 10 studs от точки, где игрок был в прошлый раз, — активность, и точка переносится (прыжок на месте, топтание на тренажёре и мелкий дрейф — нет). Любая команда игрока — тоже активность: `NetService` после проверки частоты вызывает `markActive` (= `ActivityService.touch`); клиент сам по таймеру команд не шлёт. Перерождение (смерть, буря) — не движение: якорь забывается, новое место становится точкой отсчёта. Без активности 3 минуты — игрок «отошёл». Наружу: `isActive`, `activeCount`, `idleSeconds` и сигнал `changed(player, active)` при переходе — основа для будущих правил (например, ограничить время АФК без геймпасса). Сейчас используется в метеоритном дожде: число метеоров считается по активным игрокам. Команда `ActivityStatus` — простой каждого игрока.

## Задания дня

`QuestService` выдаёт задания UTC-дня при активации профиля и в полночь, пока игрок в игре (проверка раз в 5 с). Состояние — в профиле (`quests`, схема v7: день, использована ли замена, список с целью и прогрессом), логика — чистый `Domain/Quests`, пул и награды — `QuestConfig`. Выбор: 3 задания разных видов по весам из тех, что игрок может сделать сейчас (`Context`: зона самого дальнего побеждённого стража, есть ли 3 пришельца одного стража для скрещивания, кончилась ли защита новичка для PvP-задания). Прогресс — из сигналов других служб: `CarryService.delivered` (с зоной гнезда), `BayService.hatched`, `TrainingService.trained` (секунды на площадке), `EconomyService.crossbred`, `PvpService.abilityUsed` (выбитое яйцо). Прогресс уходит клиенту не чаще раза в секунду, выполненное задание — сразу.

Награда — `Quests.reward`: минуты задания × доход в секунду (не меньше `MIN_REWARD_COINS`) и × скорость тренажёра; монеты — через `Wallet.earn` (двигают доску), очки — в `trained`. Считается в момент «Забрать»; клиент показывает ту же формулу по своей копии профиля. Команды `ClaimQuest`, `RerollQuest` (одна замена в день, не для выполненного) идут через калитку `NetService`; клиенту — `QuestsChanged`, `QuestRewarded` и задания в снимке профиля. Окно — `QuestController` + `UI/QuestWindow` (окно `NeonWindow`, бриф `docs/design/screens/quests.md`: три карточки рядом, замена — вторым нажатием после «Точно?»), кнопка «Задания» над кнопкой отсека (с числом наград, которые ждут), клавиша J. Аналитика: экономика с источником `Quest`, событие `QuestDone` с видом задания. `lune run balance` считает профиль «free + quests» по той же формуле.

## Подарок за вход

`LoginGiftService` держит серию из 7 UTC-дней (`Domain/LoginGift`, профиль v8 `loginGift`: день последнего подарка и его номер в серии). Статус (`status`: доступен ли, какой день серии, сброшена ли) уходит клиенту при активации, в полночь онлайн (проверка раз в 5 с) и после «Забрать»; в снимке профиля — тоже. Награда дня — `Domain/PlayReward.worth` (та же формула, что у заданий): минуты дохода и тренажёра по `LoginGiftConfig.MINUTES`; на седьмой день в том же изменении профиля — редкое среднее яйцо в инкубатор от самого дальнего стража, с которого была доставка (`bestPost`). Пропуск дня — серия с первого дня, после седьмого — новый круг. Команда `ClaimLoginGift` идёт через калитку `NetService`; клиенту — `LoginGiftChanged`, `LoginGiftRewarded`.

Клиент: `LoginGiftController` открывает экран сам, когда подарок стал доступен (с задержкой 1,5 с и не поверх «С возвращением!» — `BayWindowController.welcomeOpen`), кнопка «Подарок» над «Заданиями» с бейджем. `UI/LoginGiftWindow` (окно `NeonWindow`, бриф `docs/design/screens/login-gift.md`): 7 плиток в ряд (взятые — бледные с галочкой, сегодняшняя золотая и пульсирует, будущие показывают награду, седьмая шире и с яйцом в цвете редкости), по «Забрать подарок» плитка «лопается» и разлетаются искры. Аналитика: экономика с источником `LoginGift`, событие `LoginGift` с днём серии. `lune run balance` — профиль «free + daily» (задания и подарок).

## Ивенты на сервере

`EventService` ведёт часы каждого ивента из `EventConfig` (`Domain/EventClock`: тишина → предупреждение → ивент → тишина; промежуток считается от конца ивента до начала следующего, предупреждение — его последняя часть). Часы свои на каждом сервере, анонс — только своему серверу. Состояние для клиентов — атрибуты папки `ReplicatedStorage.Events` (по дочернему `Configuration` на ивент: `Phase`, `EndsAt` в серверном времени, `Zone`, `Position`), так что зашедший посреди ивента сразу видит таймер. Что ивент делает в игре — дело слушателей `EventService.changed`; место ивента (зону и точку) даёт placer, который ставит служба ивента (`setPlacer`). Ивент с `scheduled = false` по часам не идёт (пока у него нет игрового эффекта), но запускается командами `StartEvent`, `QueueEvent`. Аналитика: `EventSeen` (ивент) каждому игроку сервера.

Клиент: `EventController` читает атрибуты и показывает: строку сверху с обратным отсчётом (`UI/EventBanner`, `Duration.clock`) — во время предупреждения и ивента, а у ивентов с `alwaysShowTimer` всегда; большой анонс при предупреждении и старте (с названием зоны, если есть); метку на экране к месту ивента (`UI/ScreenPin` — та же метка, что маяк станции). Ивент, который идёт во многих местах сразу, публикует их спотами (`EventService.showSpot`/`hideSpot` → `Vector3Value` с атрибутом `Zone` в папке `Spots` ивента): пока споты есть, клиент вместо метки ивента ставит по метке на зону — к ближайшему к игроку споту этой зоны (`Domain/EventSpots`), с названием зоны (решение 053); если у ивента есть `spotAnnounceKey`, каждый новый спот ещё и объявляется. Все метки ивентов за кадр раздвигаются, чтобы не закрывать друг друга (`ScreenPin.locate` → `ScreenMarker.separate` → `pin.show`): ближняя на месте, дальние отходят к середине экрана. Цвета — `EventLooks`.

**Солнечная буря** (`StormService`, `StormConfig`): слушает `EventService.changed` для `Storm`. На старте ставит атрибут workspace `FlightRangeLimit` = граница станции — симуляция полёта (`SpaceSimulation`) упирается в него, как в край карты (`Bounds.limitVelocity` от центра купола), — и `BayService.setHatchRate(30)`: каждый тик инкубатора продвигает яйца на лишние `dt × 29` (`Bay.advanceIncubator`). Кто в космосе (атрибут `InSpace`), того `CarryService.returnEgg(…, "Storm")` (яйцо сразу в гнездо, не выпавшее) и `Player:LoadCharacterAsync()` переносят на точку спавна, плюс тост `StormTeleport`. Пока инкубаторы ускорены, каждый тик `BayService` без перестройки отсека обновляет атрибуты `HatchAt` яиц и шлёт хозяину `BayChanged` — таймеры (`Duration.clock`, мм:сс) видимо бегут быстрее. По окончании атрибут снимается, скорость инкубаторов — 1. Вид границы в бурю — клиент (`StationBorderController`, `BorderLooks`): граница краснеет, оболочка плотнеет, кольцо толще; а так как оболочку шара изнутри не видно, подлетающему к границе показывается красная «стена» силового поля — диск на границе прямо по курсу, тем плотнее, чем ближе.

**Метеоритный дождь** (`MeteorService`, `MeteorConfig`, `MeteorLooks`, `Domain/MeteorShower`): раз в 15–25 минут, предупреждение 30 с, дождь 2 минуты. У ивента `after = "Storm"`: когда его промежуток прошёл, он ждёт конца ближайшей бури (`EventService`: `waiting` — часы без конца; когда буря входит в тишину — `released`, и сразу предупреждение), так что дождь целиком идёт в тишине между бурями (тест в `Configs.spec`); `QueueEvent` и `StartEvent` бурю не ждут. Placer выбирает направление от станции — полосу; метка — в середине первой зоны на ней, зоны у места нет (`EventService.Place.zone` необязательна; `StartEvent("Meteor", зона)` — полоса через точку в этой зоне). На старте `MeteorShower.eggCount` даёт 2 метеора на активного игрока сервера (`ActivityService.activeCount`: отошедшие не считаются), от 4 до 16; `zones` раздаёт их по зонам по кругу от станции, `fallTimes` — по метеору каждые 3 с (`FALL_STEP_SECONDS`), первый — через шаг после старта, чтобы анонс дождя успели прочитать; полный дождь (16) падает за 48 с, остальное время — на кражу (тест в `Configs.spec`: не больше половины дождя). Метеор (`MeteorLooks.STREAK`, твин сверху наискосок) падает в точку полосы в кольце своей зоны: до 150 studs вбок от линии, по высоте — как гнёзда, не ближе 60 studs к любому гнезду, кратеру и месту падения другого метеора (12 попыток, иначе не падает). На месте — **кратер**: `WorldService.buildCrater` (обожжённый камень с чашей, `MeteorLooks.CRATER`) и `NestService.addCrater(site, "Meteor")` — гнездо как все (тег, атрибуты, яйцо из лута зоны с вариантом), грейд — ближайшего обычного гнезда той же зоны. По сигналу `NestService.added` `GuardianService` ставит над кратером стража этого поста, по `removed` убирает. Пока яйцо в кратере (атрибут `HasEgg` модели), `MeteorService` держит его спотом ивента — игроки видят метку зоны; о каждом новом кратере — анонс «Новый кратер в зоне …» (`EventConfig.spotAnnounceKey`: клиент объявляет спот, когда он появляется впервые за ивент, а не когда возвращается вместе с яйцом). Кратер не растит новое яйцо: доставка (`eggDelivered`) убирает его сразу. В конце дождя `MeteorService` вызывает `retireCrater` для каждого своего кратера: кратер с яйцом на месте исчезает, с яйцом в пути — когда яйцо доставят или оно вернётся (`returnEgg`). Яйцо несёт вариант до инкубатора (`NestService.takeEgg` → `CarryService.Egg.variant` → `EggRecord.variant`, профиль v10) и вылупляется в метеоритного пришельца; метеоритное яйцо горит (`EggModel`, `EggLooks.METEOR`). Скрещивание — только одного грейда и одного варианта (`Crossbreed.mismatch`/`check`, отказ `MixedVariants`); то же правило клиент использует для подсказок и затемнения в окне отсека. Страж держится за одного вора, пока тот не пойман и не в безопасности, потом берётся за ближайшего (`GuardianBrain.pickTarget`); у гнезда и кратера одно яйцо, так что это важно только для тестовых яиц. `lune run balance`: одно метеоритное яйцо с дождя из зоны самого дальнего побеждённого стража.

**Звёздный змей** (`SerpentService`, `SerpentConfig`, `SerpentLooks`, `World/SerpentModel`, `Domain/SerpentHunt`, `Domain/StarEgg`, `Domain/SerpentBody`, клиент — `SerpentController`, `World/SerpentVisual`; решения 054, 055, 093): раз в 15–25 минут, `after = "Storm"`, как дождь (оба могут прийти после одной бури), предупреждение 30 с, охота 3 минуты. Placer — случайная зона из `SerpentConfig.ZONES` (все, кроме Пояса обломков) и точка в середине её кольца; **зона змея на всю охоту** — его скорость, грейд его яйца и кольцо, по которому он бродит, куда бы его ни загнали (решение пользователя от 2026-11-05). На старте сервер ставит голову змея — физический мовер, как страж (`LinearVelocity` + `AlignOrientation`, `SetPredictionMode Off`), модель `StarSerpent` в `workspace.World` с `ModelStreamingMode = Persistent`, чтобы её видели с любого расстояния; змей не залетает ближе `HUNT_RADIUS` (внешний край Пояса обломков, `Bounds.keepOutside`) и дальше `OUTER_RADIUS` (`Bounds.limitVelocity`). **Где звёздное яйцо — `Domain/SerpentHunt`:** `Inside(hits)` → `Out` → `Delivered`; от этого поведение. *Яйцо внутри:* змей убегает от ближайшего игрока в космосе ближе `FLEE_RADIUS` (`Pursuit.fleeVelocity`) со скоростью `SerpentConfig.fleeSpeedIn(зона)` — 0,9 скорости полёта игрока с ⚡ змея, а ⚡ змея — ⚡ стража `POWER_POST` (3-го) его зоны (`powerIn`); без игроков рядом бродит по кольцу своей зоны со скоростью `ROAM_SPEED`. Голова — **существо PvP** (`PvpService.addCreature`: радиус `HIT_RADIUS`, атаки попадают в ближайшую точку поверхности — `Abilities.nearestPoint`; правила между игроками на существ не действуют, только «из-под купола не бить» — `Pvp.creatureRefusal`). Удар, гарпун или бомба — попадание (атрибут `LastHit` на голове — клиент вспыхивает); `HITS_TO_DROP` попаданий на весь сервер — яйцо вылетает выпавшим (`CarryService.spawnLooseEgg`): `StarEgg.roll` по зоне змея — грейд среднего стража зоны, редкость по добыче зоны не ниже `STAR_EGG_MIN_RARITY`, удача `STAR_EGG_LUCK` (едет с яйцом: `CarryService.Egg.luck` → `EggRecord.luck`, профиль v11, при вылуплении `EggConfig.luckOf`); яйцо с удачей искрится везде (`EggModel`, `EggLooks.LUCKY_SPARKLE_COLOR`). *Яйцо снаружи:* змей сторожит его, как страж (`GuardianBrain` с `SerpentConfig.BRAIN`): висит над выпавшим, гонится за носителем по формуле стражей (`Prey.chaseSpeed` против `powerIn(зона)`), ловит — `Prey.strike`, `CarryService.dropEgg(..., "Serpent")`, `Knockback` с `HitBy = "Serpent"` (тост «Тебя схватил змей!»). **Дом яйца** — `Domain/EggHomes`: у яйца в `CarryService` вместо гнезда дом `StarSerpent` (`EGG_HOME_ID`), который змей регистрирует на время охоты; через него `CarryService` берёт грейд, возвращает яйцо (выпавшее пролежало `LOOSE_SECONDS`, носитель ушёл — яйцо снова внутри, попадания с нуля) и сообщает о доставке. Доставка — анонс и досрочный конец ивента (`EventService.stop`). Время вышло: яйцо внутри — уходит со змеем; выпавшее — лежит без охраны `STAR_EGG_LINGER_SECONDS` (30 с), потом убирается (`CarryService.removeLooseEggs`), если его никто не взял; в руках — остаётся у игрока. Дом живёт, пока яйцо не доставят или не потеряют; следующая охота убирает выпавшее яйцо прошлой. Клиентам — атрибуты папки ивента (`EventService.setDetail`): `StarEgg`, `SerpentHits`, `StarEggBy`, `SerpentEnding`; `SerpentController` по ним меняет заголовок метки («Звёздный змей 2/3» → «Звёздное яйцо», `EventController.setPinTitle`) и объявляет выбивание, возврат, доставку и конец (`EventController.say`). ## Размер станции

Станция задаётся двумя числами (решение 068) — радиусом центральной платформы `StationSize.PLATFORM_RADIUS` и радиусом острова `ISLAND_RADIUS`; остальное — цепочкой (`Config/StationSize`, чистые числа для Lune): купол = своя платформа × 1,5; 8 островов (по одному на игрока, `ISLAND_COUNT` = `ServerConfig.MAX_PLAYERS`) на кольце вокруг центра, их купола в `ISLAND_GAP` друг от друга; граница станции = кольцо островов + купол острова + запас (на ней останавливаются стражи и кончается полёт в бурю); спавн новичка — доля центральной платформы. Карта идёт от границы: кольца зон — `ZoneConfig` «столько-то за границей», поле астероидов и край карты — `WorldConfig` от границы и последней зоны, чёрная дыра — от края карты; киоск и доска монет — доли центральной платформы. `StationConfig` строит из этих чисел формы: `STATION` (центр), `ISLANDS` и их рамки `ISLAND_FRAMES`, `STATIONS` (центр + острова) — под любым из куполов ходьба и нет расхода кислорода (`Zones.nextInSpace` по списку). Отсек строится в рамке своего острова (`BayModel.origin`); остров закрепляется за игроком при входе (`BayService.reserve`), его спавн — `Player.RespawnLocation` (смерть и буря возвращают домой). Яйцо засчитывается на центральной станции или на своём острове (`CarryService`, `Zones.stationAt`); выпавшее яйцо выталкивается из-под всех куполов.

## Индекс пришельцев

Все пришельцы игры — один реестр `AlienConfig`; индекс строит из него наборы стражей (`IndexConfig.SETS`: грейд, вариант и его пришельцы — виды × 5 ступеней, сейчас 15; `SETS_BY_ID`) и ничего своего не заводит. Виды грейда — `grade.kinds` (`AlienConfig.KINDS`, решения 075, 080): первый — основной (детёныш стража), у каждого свой вес вылупления (`weight`; сейчас три вида, 60/30/10, `grade.kindEntries`), доход у них одинаковый; новый вид — строка в конце списка стража в `POST_KINDS`. Пришельцы — в двух вариантах (`AlienConfig.VARIANTS`): обычные (`IceRings1.iceWorm.Rare`; `grade.aliens` — основной вид) и метеоритные (`IceRings1.iceWorm.Rare.Meteor`, доход ×2) — `grade.variants[variant][kind][tier]`. Миграция v15 → v16 делает пришельцев из старых сохранений основным видом стража. `IndexService` отмечает пришельца найденным (`Domain/AlienIndex.discover`), когда он впервые пришёл к игроку: `BayService.hatched`, `EconomyService.crossbred`, команда `GiveAlien`. Профиль v10 `index`: `found` — id → награда взята, `sets` — id наборов, за которые награда взята (`AlienIndex.setId`: `"3"` — обычный набор грейда 3, `"3.Meteor"` — метеоритный); миграция v8 → v9 отмечает найденными (с взятой наградой) пришельцев, которые у игрока уже есть, v9 → v10 переводит грейды наборов в id. Награды забираются в окне: за пришельца — минуты дохода по ступени (`IndexConfig.REWARD_MINUTES`), за полный набор — `SET_REWARD_MINUTES`; только монеты, через `PlayReward.of/pay`. Команды `ClaimIndexAlien`, `ClaimIndexSet` через калитку `NetService`; клиенту — `IndexChanged`, `IndexRewarded` и индекс в снимке профиля.

**Модели пришельцев** (решение 081, `docs/design/BLENDER_ROBLOX.md`, 5a): голые модели видов — `assets/aliens/<вид>.rbxm` (10 питомцев: ступени 0–4 и метеоритные m0–m4), их пишет `lune run aliens` из файла, сохранённого в Studio, вместе с отпечатками `src/server/World/AlienModels.json` и общим `out/Aliens.rbxm`. В плейс они попадают вставкой в `ServerStorage.Aliens` (Rojo теряет сетки MeshPart); `AlienModel.checkPlace` в Studio предупреждает о недостающих и устаревших видах. `World/AlienModel` берёт вид и вариант пришельца, один раз одевает его (`World/AlienDress`, перенос галереи прототипа) и дальше клонирует: размер — `alien.scale` с вычтенным ростом ступени из Blender (`AlienLooks.MODELS`), самая нижняя видимая точка — на точке места, морда — к центру острова; невидимая деталь `Body` по габаритам — для таблички дохода и подсказки «Забрать». Ширина места — по модели (`AlienModel.widthOf`); на стеллаже пришелец уменьшается до ниши (`BayLooks.SHELF_ALIEN_FILL`, `AlienModel.heightOf`). Вид без модели — шарик-заглушка. **Движение** — клиент, `AlienMotionController` (перенос галереи прототипа): берёт пришельцев по тегу `BayConfig.ALIEN_TAG` (модель приходит целиком, `ModelStreamingMode = Atomic`), читает роли деталей и шарниры (`hinge<Имя>`) и двигает питомцев одним `BulkMoveTo` за кадр с детализацией по расстоянию от камеры (`PetMotion.detail`, `AlienLooks.MOTION`): ближе `NEAR` — всё и каждый кадр; до `FAR` — только главные слои частиц (`MAIN_EFFECTS`), без света, движение через кадр; дальше (и чужие острова) — питомец стоит без частиц, света и картинок; переход с запасом `DETAIL_MARGIN`, чтобы не мигало. Движение: покачивание и поворот к игроку, моргание, движения семейств, крылья с пыльцой, дроны по своим петлям, кометы, руна и медаль. Сервер модель не двигает. Кривые (моргание, щелчок, прыжок слизня) — `Domain/PetMotion`, с тестами на непрерывность. Длины, сделанные на масштабе одевания (орбиты комет, покачивание), растут с питомцем (`Model:GetScale()`). Металл и лавовая кожа — заготовки из `default.project.json` (`MaterialService.PetMetal`, `ServerStorage.AlienSkins.Lava`): карты текстур сервер игры задавать не может.

**Пришельцы и сеть** (замер 2026-11-10, скамья 30 пришельцев): одевание поделено (`Shared/World/AlienDress`) — сервер готовит питомца (краски, металл, лава, крылья, деталь `Body`; 73 объекта на питомца), эффекты (частицы, свет, кометы, руна, медаль) делает каждый клиент у себя (`adornLocally` в `AlienMotionController`) и по сети они не ходят. Пришелец на полу (атрибут `Plain`) — только модель: без эффектов и движения. Пересборка острова (`BayService.refresh`) не трогает пришельцев, оставшихся на месте: переставляет их (`AlienModel.place`, атрибут `Pivot`, клиент двигает питомца вокруг новой опоры) или строит заново только при смене вида или размера; одна пересборка с 30 пришельцами — ~100 объектов вместо ~5000 (раньше канал телефона забивался и сервер откатывал персонажа). Движение: что делает каждая деталь, считается один раз при появлении питомца (`Mover`), невидимые детали не двигаются, дальше `MOTION.SMOOTH` от камеры — через кадр; 30 питомцев — 2,4 мс за кадр в Studio вместо 4,5.

Клиент: `IndexController` + `UI/IndexWindow` (окно `NeonWindow`, бриф `docs/design/screens/index.md`): слева переключатель «Обычные» / «Метеоритные» (бейдж наград у каждого) и четыре зоны (счётчик, полоса, точка — ждёт награда); справа шесть стражей выбранной зоны, у каждого 5 клеток по ступеням: неизвестный — «?», найденный — шарик с глазами в цвете ступени, новый — с золотой рамкой и свечением, по нажатию — награда; полный набор — золотая кнопка «●+N» в строке, забранный — «✓ Собран». Открывается там, где ждёт награда, иначе у самого дальнего стража с находками (`AlienIndex.openingSet`). Кнопка «Индекс» в колонке меню с бейджем `AlienIndex.waiting` (новые находки и собранные наборы). Новые находки, пришедшие разом, — один тост. Аналитика: событие `AlienFound` (ступень, зона), экономика с источниками `IndexAlien`, `IndexSet`. `lune run balance` — в профиле «free + daily».

## Доска монет

`LeaderboardService` раз в секунду смотрит `coinsEarned` игроков сервера: пишет его в колонку `●` стандартного списка игроков (`leaderstats`, строка `BigNum.format`: число список показывает плохо, 1.5e15 обрезает) и пересобирает строки доски. Общая доска по всем серверам лежит в `OrderedDataStore` `CoinsEarned_v1` (`Data/RankStore`): ключ — user id, значение — очки `Domain/Leaderboard.score`, десятичный логарифм монет в миллионных (хранилище принимает только целые; порядок сохраняется, обратно — около 6 знаков). Каждый сервер пишет изменившиеся очки раз в 5 минут и при выходе игрока, читает топ-10 раз в 2 минуты; игроки на сервере заменяют свои строки из хранилища точными числами (`Leaderboard.top`). Отображаемые имена чужих игроков — `UserService:GetUserInfosByUserIdsAsync`, с кэшем.

Табличка на станции — `World/LeaderboardModel` (`LeaderboardLooks`, тег `CoinBoard`), строки — JSON в `StringValue` `Rows` внутри модели (строковые атрибуты здесь ограничены 50 символами). Рисует клиент (`CoinBoardController`, `UI/CoinBoard`: `SurfaceGui` на передней грани панели) на своём языке и подсвечивает свою строку. Сбой хранилища только откладывает обновление: профиль от доски не зависит (CONVENTIONS, «Данные»). В Studio, где у неопубликованного плейса нет хранилищ, доска переходит на хранилище в памяти и показывает игроков этого плейтеста (`[LeaderboardService] No data stores…` в Output).

## Покупки за робуксы

Каталог (решения 061, 062) — `MonetizationConfig`: ID пропусков и покупок по `game.GameId` (у Dev и Prod свои; в игре, которой там нет, в том числе в непубликованном плейсе, покупки выключены), настройки пропусков `PASS_TUNING`, пакеты ⚡, ступени. Что делает покупка — чистый `Domain/Purchases` с тестами: эффекты пропусков (`passEffects`, `trainerRate` — одна формула для тренажёра, офлайна, пакетов и таблички), пакет ⚡, «готово сейчас» с запасным яйцом, ступени мест, «Забрать ×2» со ступенью по размеру награды (`doubleTier`, решение 064: ступень считает `OfflineService` и шлёт в `OfflineReward`; чек ступени ниже платит до её предела), компенсация. Цены в коде не хранятся: их задаёт Creator Hub, клиент спрашивает у Roblox (`GetProductInfoAsync`), так работает и Managed Pricing.

Сервер — `PurchaseService`, единственный `ProcessReceipt` в игре: ждёт активный профиль, пропускает уже выданный чек (`purchaseIds`), выдаёт покупку и отмечает чек одним `DataService.update`, ждёт сохранения (`SessionManager.waitUntilSaved`) и только тогда отвечает `PurchaseGranted`; иначе `NotProcessedYet`, и Roblox спросит снова. Пропуски проверяются у Roblox при входе (`UserOwnsGamePassAsync`, с повтором) и отмечаются при покупке (`PromptGamePassPurchaseFinished`); копия — в профиле. Всем клиентам — атрибуты игрока `Passes` и `TrainerMultiplier`. Выданная покупка — событие `Purchased` (для уведомления), аналитика `Purchase` и `PurchasePrompt`.

Клиент — `PurchaseState` (каталог, цены, какие пропуски есть, запрос покупки) и `StoreController` с окном `UI/StoreWindow` («Магазин», бриф `docs/design/screens/store.md`: пропуски слева, разовые покупки 2 × 2 справа; кнопка в меню и «Больше ⚡» у цели роста). Цены со знаком `R$`, который `UI/IconText` рисует иконкой робукса (`Locale/Marks`). Цены `PurchaseState.refreshPrices` спрашивает у Roblox заново, когда они появляются на экране (не чаще раза в 30 с): Managed Pricing меняет их во время игры. Покупки на месте: на греющемся яйце — подсказка «Вылупить за … R$» (`BayService` ставит её с атрибутом ступени `ReadyNowTier`, слова с ценой и запрос покупки — `EggPurchaseController`); это единственное место покупки «готово сейчас»; в окне отсека — место за робуксы; на экране возвращения (`UI/WelcomeBack`, компактное окно, бриф `docs/design/screens/welcome-back.md`) — «×2 за R$ …». Перед окном покупки Roblox клиент шлёт `PurchasePrompted` (откуда предложено и какое яйцо для «готово сейчас»): у покупки Roblox нет параметров, поэтому выбор яйца сервер запоминает заранее. Покупка для выбранного яйца вылупляет его сразу (`BayService.hatch`, решение 063; в `Purchased` — `hatched`).

## Туториал

Решение 065. Что игроку делать сейчас, решает чистый `Domain/Tutorial`: из пройденных вех профиля (`tutorialStep`) и того, несёт ли он яйцо, выходит подсказка (`Steal`, `CarryHome`, `Hatch`, `Train`, `StealStronger`, `CarryHomeStronger`, `Done`). Первое яйцо быстрое прямо в `BayService.addEgg` (`Tutorial.hatchSeconds`), внутри того же изменения профиля. Воронка `Tutorial` в аналитике — `MetricsService.tutorialStep` (одна сессия на аккаунт, шаг = веха + 1). Команда `SetTutorialStep`.

Клиент — `TutorialController` (бриф `docs/design/screens/tutorial-arrows.md`): строка подсказки с точками шагов и иконкой шага (`UI/TutorialPanel`, над баллоном кислорода; номер шага — `Tutorial.stepOf`), метка `UI/ScreenPin` на цели и в мире — дорожка из бегущих шевронов от персонажа к цели и подсветка цели (`UI/GuidePath`: `Beam` на Terrain, `Highlight` под камерой; видит только сам игрок). Цели: выпавшее яйцо игрока, если его страж засчитывается шагу и игрок его обгоняет (атрибуты выпавшего яйца `Grade`, `DroppedBy`; `Tutorial.backToDropped`), иначе ближайшее гнездо нужного стража с яйцом (атрибут гнезда `Grade`); свой отсек (инкубатор), пока несёшь яйцо, своё яйцо в инкубаторе, свой тренажёр. «Готово» сразу после другой подсказки — игрок только что прошёл туториал: прощальная строка на 8 с; «Готово» при входе — ничего.

## UI (клиент)

- Компоненты на Vide в `src/client/UI`: без ключей локализации и без сетевых вызовов — тексты приходят готовыми, действия — колбэками. Контроллеры (`HudController`, `BayWindowController`) собирают тексты через `Text.get`, читают `ProfileState` и отправляют команды через `Remotes`.
- `Theme` — палитра и шрифт: `Theme.NEON` — утверждённый стиль ([design/DESIGN.md](design/DESIGN.md)), плоские токены — грейбокс окон до их брифов. `Layout` — `UIPadding`/`UISizeConstraint`/`UIStroke`, которых нет в типах Vide, и детали стиля: масштаб экрана (`screenScale`), обводка текста, цветное стекло (`glass`). `Icons` — номера загруженных иконок (белые, цвет даёт `ImageColor3`; исходники SVG в `assets/ui`, `lune run icons`). Переиспользуемые детали: неоновые `ResourcePill`, `GoalCard`, `ActionButton`; старые `Button`, `WorldLabel`, `AlienCard`, `Toasts`.
- Метка своего острова (`HomeBeaconController`, решение 069; раньше — маяк станции) — экранная метка, а не BillboardGui: каждый кадр точка над куполом своего острова проецируется камерой, `Domain/ScreenMarker` (чистый, с тестом) решает, стоять метке над куполом или у края экрана со стрелкой. Так метка видна с любого расстояния и не зависит от стриминга острова.
- Имена пришельцев и яиц собирает `Locale/Names` (чистый модуль с тестом): пришелец — «ступень · страж», пока у пришельцев нет своих имён.

## Локализация

- Все строки — в `src/shared/Locale/Strings.luau`, по ключу `область.имя.тип`, сразу на русском и английском. Множественное число — формы по `{count}`.
- Код берёт текст только через `Text.get(locale, key, args)`. Тип ключа выводится из таблицы строк, поэтому опечатка в ключе — ошибка проверки типов.
- Язык игрока: `Text.resolveLocale(player.LocaleId)` на сервере, `LocalizationService.RobloxLocaleId` на клиенте. Всё, что не русский, — английский.
- Свой модуль вместо `LocalizationTable`: строки проверяются в Lune (`lune run content`), формы множественного числа и подстановки работают одинаково везде.
