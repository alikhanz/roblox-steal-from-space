# Правила разработки

Обязательны для всего кода в репозитории. Если правило мешает, его меняют здесь осознанно, с записью в [DECISIONS.md](DECISIONS.md), а не нарушают молча.

Приоритеты: **корректность → читаемость → производительность → скорость разработки.**

## 1. Флоу

- **Код правится только в файлах.** Studio используется для запуска и тестов. Правки скриптов в Studio при подключённом Rojo перетираются.
- **`lune run check` перед каждым коммитом.** Коммит с красной проверкой запрещён.
- Ветка `master` — только рабочий код. Работа ведётся в ветках `<тип>/<кратко>`: `feat/jetpack-flight`, `fix/egg-drop`, `chore/tooling`.
- Коммиты — [Conventional Commits](https://www.conventionalcommits.org): `feat:`, `fix:`, `refactor:`, `test:`, `docs:`, `chore:`. Сообщение на английском.
- Одна ветка = одна логическая задача. В `master` вливается целиком после зелёной проверки.
- Две отдельные игры (experience): **Dev** для разработки и тестов, **Prod** для игроков. У них разные DataStore.

## 2. Язык

- Код, идентификаторы, комментарии, коммиты — **английский**.
- Документация в `docs/` — **русский**.
- Тексты для игроков — только через локализацию, на русском и английском (см. [STYLE_TEXT.md](STYLE_TEXT.md)).

## 3. Стиль кода

- `--!strict` в каждом файле. Используется новый type solver.
- Форматирование — StyLua (`stylua.toml`), линтер — Selene (`selene.toml`). Спорить со StyLua нельзя: `lune run format`.
- Имена:
  - `PascalCase` — модули, сервисы, контроллеры, типы, файлы модулей;
  - `camelCase` — функции, методы, локальные переменные, поля;
  - `SCREAMING_SNAKE_CASE` — константы модуля;
  - булевы — с `is`/`has`/`can`: `isCarryingEgg`.
- Имя файла = имя модуля. Один модуль — одна ответственность. Ориентир: до ~300 строк в модуле, функции короткие.
- **Никаких магических чисел.** Баланс, цены, тайминги, шансы — в `src/shared/Config`.
- Публичный API модуля типизирован явно (`export type`, аннотации параметров и результатов). Внутренности наружу не торчат.
- Комментарии объясняют **зачем**, а не **что**. Очевидный код не комментируется.
- Запрещено: `_G`, `shared`, глобальное изменяемое состояние, `wait`/`spawn`/`delay` (только `task.*`), `getfenv`/`setfenv`, `loadstring`.
- UI на Vide описывает свойства и дочерние элементы в одной таблице. В таких файлах в начале стоит `--# selene: allow(mixed_table)` — только в UI-компонентах, больше нигде.
- Конфиги заморожены (`table.freeze`), поэтому типы, которые их принимают, объявляют поля `read`.
- **Одна правда — одно место (DRY).** Каждое правило, формула и список живут ровно в одном модуле, остальные берут оттуда, а не повторяют у себя. Нашёл копию — сведи её к общему модулю в том же шаге. Действующие точки правды:
  - **пришельцы** — только реестр `AlienConfig` (`ALIENS`, `GRADES`, `TIER_ORDER`): индекс, вылупление, скрещивание, калькулятор баланса, тексты берут пришельцев из него и не собирают своих (решение 047). Новые пришельцы (ивентовые) добавляются в этот же реестр;
  - **монеты в профиль** — только `Domain/Wallet.earn`; **награды «минуты своей игры»** — только `Domain/PlayReward` (сервер платит, клиент показывает через `State/Pace`, калькулятор считает);
  - **яйцо в инкубатор** — только `Domain/Bay.addEgg`; **сутки игры** — только `Domain/UtcDay`;
  - **форма сетевых данных** — `net/remotes.zap`: клиент берёт типы из сгенерированного `Remotes`, а не переписывает их;
  - **окна меню** — `UI/Window`, **кнопки левой колонки HUD** — `Layout.placeInMenu`.
- Ошибки:
  - `pcall` — только на границах с внешними сервисами (DataStore, Marketplace, HTTP, Teleport);
  - ошибка программиста — `assert`/`error` с понятным текстом;
  - **тихие сбои запрещены**: если что-то пошло не так, это видно в логе.

## 4. Структура и зависимости

- Слои (подробно в [ARCHITECTURE.md](ARCHITECTURE.md)):
  `Config` (данные) → `Domain` (чистая логика) → `Services`/`Controllers` (связь с Roblox) → `Net` (Zap).
- **`Domain` не знает о Roblox.** Никаких `game`, `Instance`, `workspace`, `task`. Только Luau. Поэтому домен тестируется в Lune.
- Исключение — типы данных вроде `Vector3`: домен может **принимать** их и работать с ними (`+`, `Dot`, `Unit`, `Lerp`), но **не создавать** через глобал (`Vector3.new`, `Vector3.yAxis`) — в Lune его нет. Нужные константы передаются параметром (пример — `up` в `Flight.direction`). В тестах `Vector3` берётся из `@lune/roblox`; он хранит float32, поэтому допуски для долгих расчётов — около 1e-3.
- `require` внутри `src/shared` — **строковые относительные** (`require("./BigNum")`, `require("../Config/Rarity")`): они одинаково работают в Roblox и в Lune.
- **В коде, который тестируется в Lune, нет `init.luau`.** Roblox и файловая система разрешают его пути по-разному.
- Между сервисами Roblox (`ReplicatedStorage` ↔ `ServerScriptService`, пакеты) — `require` через инстансы.
- Чистая логика на сервере (как `SessionManager`) не делает `require` модулей из `ReplicatedStorage` и Roblox API: всё нужное получает параметрами. Так она тестируется в Lune.
- Общий код в `src/shared`, который тестируется, не обращается к глобалам Roblox (`task`, `game`, `workspace`): нужные функции передаются параметром (пример — `spawn` в `Lifecycle.run`).
- Зависимости — только через Wally (`wally.toml`), версии закреплены в `wally.lock`. Новая зависимость = запись в [DECISIONS.md](DECISIONS.md) (зачем, почему эта).
- Инструменты — только через Rokit (`rokit.toml`).

## 5. Сервер — единственный источник истины

- Клиент присылает **намерения** («хочу взять яйцо в гнезде N»), сервер решает результат.
- Каждый входящий запрос проходит три фильтра, по порядку:
  1. **лимит частоты** на игрока и тип запроса;
  2. **проверка типов и диапазонов** (Zap проверяет структуру, мы — смысл: конечные числа, допустимые ID);
  3. **проверка возможности**: может ли этот игрок сейчас это сделать (дистанция, кулдаун, состояние, владение).
- Команды, меняющие прогресс, принимаются **только при активной сессии профиля** (`Active`, см. раздел 7).
- Если обработка ждала (`yield`), перед применением результата сессия и условия **проверяются заново**.
- Команды одного игрока обрабатываются **по порядку**.
- Взаимодействия движка (`ProximityPrompt`, `ClickDetector`, физика) — тоже входы от клиента и проверяются так же.
- Позиция физического объекта, которым владеет клиент, **не доверенная**. Ценные события (подбор яйца, попадание гарпуна, сдача у шлюза) проверяются на сервере.

### Симуляция (Server Authority)

Код, привязанный через `RunService:BindToSimulation` (сейчас — `SpaceSimulation`), выполняется и на сервере, и на клиенте, в том числе повторно при откатах. Поэтому в нём:
- только API с меткой **Simulation Access**;
- состояние — **в атрибутах** предсказываемых инстансов (персонаж), а не в Lua-переменных: переменные не откатываются;
- ввод — **опросом** `InputAction:GetState()`; события `Pressed`/`Released` при откатах ненадёжны;
- **никаких** `Instance.new` для существующих объектов, `Destroy()`, смены `Parent`, `task.wait` — объекты готовит сервис заранее, удаляет в `PostSimulation`;
- время — только `deltaTime` шага или `time()`; `tick()`, `os.clock()` не синхронизированы;
- весь ввод в симуляцию — только через `InputAction`. Значения от клиента (например, направление камеры) проверяются, как любые входные данные.

### Персонаж
- Суставы аватара — физические (`AnimationConstraint`): каждая часть тела — отдельная сборка. **Перемещать персонажа — только `character:PivotTo(...)`**, никогда не `HumanoidRootPart.CFrame`: иначе двигается один корень, суставы рвутся, персонаж погибает.
- Границы зон с переключением режимов — с запасом (гистерезисом), чтобы на самой границе режим не дёргался каждый кадр (пример — `Zones.nextInSpace`).

## 6. Сеть

- Все remotes — только через Zap (`net/remotes.zap` → `lune run net`). Голые `RemoteEvent`/`RemoteFunction` запрещены.
- Реплицировать **при изменении**, не каждый кадр. Минимальные порции: «добавлено существо X», а не весь инвентарь.
- Данные игрока на клиент — наш тонкий слой на Zap: снимок при входе плюс дельты. Клиент держит копию в состояниях Vide и **не пишет** в неё.
- Владелец видит свои данные, остальные — только публичное (например, витрину отсека). Служебные поля профиля не реплицируются.
- Визуальные эффекты, звуки, твины — **только на клиенте**.
- `RemoteFunction` с сервера на клиент запрещены (клиент может не ответить).

## 7. Данные игрока

- Только **ProfileStore** (`lm-loleris/profilestore`). Прямые вызовы `DataStoreService` для данных игрока запрещены.
- Жизненный цикл сессии: `Loading → Active → Closing → Closed`, плюс `Failed`.
  - Команды, меняющие прогресс, — только в `Active`.
  - Игрок вышел во время `Loading` — поздний результат не запускает сессию, профиль корректно закрывается.
  - Сессия потеряна — изменения прекращаются, игрок выходит с понятным сообщением.
- **Ошибка чтения ≠ новый игрок.** Профиль не загрузился — игрок не играет (сообщение и выход). Никогда не даём играть на данных по умолчанию.
- Все изменения профиля — только через API `DataService` (единая граница применения). Прямые мутации таблицы профиля из других сервисов запрещены.
- Связанное изменение (списать + выдать) делается **одним участком кода без ожиданий** внутри.
- В профиле есть `schemaVersion`. Изменение формата = пошаговая миграция `vN → vN+1`, проверенная тестом на старых сохранениях и безопасная при повторном запуске. Данные новее, чем знает сервер, или повреждённые — не трогаем и не затираем.
- `Reconcile` только добавляет новые поля и миграции не заменяет.
- **Профиль — источник истины, мир — его отображение.** Не загрузилась модель — запись в профиле остаётся.
- Состояние полёта (яйцо в руках, кислород) **не сохраняется**. Вышел с яйцом — оно вернулось в гнездо.
- Покупки (Developer Products):
  1. дождаться активного профиля;
  2. проверить, не обработан ли этот `PurchaseId`;
  3. награда и отметка о чеке — одно изменение профиля;
  4. дождаться подтверждённого сохранения по документированному механизму ProfileStore;
  5. только потом `PurchaseGranted`. Нет активного профиля — `NotProcessedYet`.
- Лидерборды — производные данные (`OrderedDataStore`). Их сбой не меняет профиль.
- Перед релизом проходим [матрицу отказов](#11-матрица-отказов-перед-релизом).

## 8. Экономика и числа

- Все деньги, доход, цены и множители — тип **`BigNum`** (свой модуль, мантисса + порядок, точность double). Голые числа для экономики запрещены.
- Форматированная строка (`1.2K`) — только для отображения, никогда не становится значением.
- Офлайн-прогресс считается по серверному времени от сохранённой метки, с явным потолком. Один период не оплачивается дважды.
- Все ID в конфигах стабильные: название можно менять и переводить, ID — часть формата сохранений.
- Ссылки между конфигами проверяются автоматически в `lune run check` (проверка добавляется вместе с первыми конфигами).

## 9. Производительность

- **Бюджеты** (уточняются после прототипа): время серверного кадра, трафик на игрока, память клиента, число активных стражей, размер профиля. Тестируем на слабом телефоне.
- Один планировщик тиков вместо множества подписок на `Heartbeat`. У каждой системы своя частота: стражи 10–20 Гц, доход 1 Гц, ивенты по таймеру.
- Тяжёлое — не каждый кадр. Работу растягиваем на кадры (`task.wait()`).
- Стражи и эффекты активны только рядом с игроками.
- Частые объекты (яйца, снаряды, эффекты) — из пула, а не `Instance.new`/`Destroy` каждый раз.
- `.Touched` для игровой логики не используем: пространственные запросы (`GetPartBoundsInRadius`, `GetPartsInPart`) в нужный момент + проверка дистанции на сервере.
- Статичное — `Anchored`. `CanTouch`/`CanQuery`/`CanCollide` = `false`, где не нужно. `CollisionFidelity` — `Box`/`Hull`. Одинаковые меши переиспользуются.
- Тени, свет, частицы — экономно. Текстуры до 512×512.
- Каждая подписка имеет владельца и отключается. На `PlayerRemoving` чистятся все таблицы игрока.
- Код учитывает StreamingEnabled: инстанса на клиенте может не быть. `WaitForChild` без таймаута запрещён. (Радиус стриминга сейчас больше карты — решение 032, — но инстансы всё равно приходят не мгновенно и могут уйти.)
- `--!native` — только для горячих математических модулей. Parallel Luau — только если профайлер показал, что без него нельзя.
- Измеряем, а не угадываем: MicroProfiler, `debug.profilebegin`/`profileend`.

## 10. Тесты

- Доменная логика покрыта тестами в `tests/**/*.spec.luau` (Lune). Новая логика приходит с тестами.
- Для сохранений — тестовый адаптер хранилища, умеющий ошибки, задержки и неопределённый результат записи.
- Поведение в движке проверяется плейтестом в Studio (в том числе через MCP Studio), сценарии с несколькими игроками — в режиме Server & Clients.
- Межсерверные сценарии (переподключение, два сервера на один профиль) — в опубликованной Dev-игре.

## 11. Матрица отказов перед релизом

| Сценарий | Ожидаемое поведение |
|---|---|
| DataStore не ответил при входе | Стартовый профиль не записан поверх существующего, игрок получает сообщение |
| Игрок вышел во время загрузки | Сессия не стартует, профиль корректно закрыт |
| Два сервера открывают один профиль | Менять профиль может только действующая сессия |
| Быстрое переподключение | Старый сервер не затирает новый прогресс |
| Сохранение задержалось или упало | Нет ложного «сохранено» |
| Чек пришёл повторно | Награда выдана один раз |
| Сервер упал при обработке покупки | Повтор доводит покупку до согласованного результата |
| Не загрузилась модель существа | Существо остаётся в профиле |
| Спам или мусорная команда | Отклонено без изменения прогресса |
| Повторный запуск миграции | Нет двойных наград и потери данных |
| Повторный сбор офлайн-награды | Один период не оплачивается дважды |
| Вышел с яйцом в руках | Яйцо вернулось в гнездо, прогресс не тронут |

## 12. Ассеты

- Модели, взятые со стороны (Creator Store, импорт, генерация), **очищаются от скриптов** до попадания в проект.
- Модели хранятся в `assets/` (`.rbxm`), меши и текстуры — в облаке Roblox по asset ID.
- `lune run check` проверяет (добавляется вместе с первыми моделями): в моделях нет скриптов, у моделей есть обязательные атрибуты, конфиги ссылаются на существующие модели.
- Ассеты загружаются от имени владельца игры — сейчас это личный аккаунт разработчика (решение 040). Анимации проигрываются только в играх того же владельца: если игра когда-нибудь переедет в группу, все ассеты перезаливаются от группы.

## 13. Тексты для игроков

- Только через ключи локализации, никаких строк в коде UI.
- Каждая строка — на русском и английском. Языки пишутся отдельно, а не переводятся дословно.
- Правила — [STYLE_TEXT.md](STYLE_TEXT.md), термины — [GLOSSARY.md](GLOSSARY.md). Для любого текста игроку — скилл `game-copy`.
